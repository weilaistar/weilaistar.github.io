深入解析 mmap：从用户态到内核态的实现

2026-11-18 Linux 内存管理 内存映射

在上一篇文章中，我们介绍了 mmap()/munmap() 与 ioremap() 等函数的基本用途和参数含义。但 mmap() 只是冰山一角——一次 mmap() 调用，从用户态的 glibc 封装出发，究竟是如何穿过系统调用、在内核里分配虚拟地址、创建 VMA、直到真正访问时才建立物理页映射的？

本文将沿着这条调用链路，把 mmap 从用户态到内核态的具体实现完整梳理一遍。

一、用户态：mmap 的调用入口

在用户态，我们调用的是 glibc 提供的 mmap() 包装函数：

它本质上是对 mmap 系统调用的封装。在 x86_64 平台上，最终通过一条 syscall 指令陷入内核（32 位平台由于 offset 只有 32 位，历史上一度使用 mmap2 并把偏移量以页为单位传入）。glibc 只是把这些参数原样传给内核，所以真正的逻辑都在内核里完成。

mmap 是极少数「先分配虚拟内存、后按需建立物理映射」的系统调用，它几乎不做任何实体的内存拷贝，这正是它能实现零拷贝与高效文件映射的根源。

二、系统调用进入内核：ksys_mmap_pgoff

内核侧对应的入口是 SYSCALL_DEFINE6(mmap, ...)，位于 mm/mmap.c。它把 offset 右移 PAGE_SHIFT 换算成页号（pgoff）后，交给核心函数 ksys_mmap_pgoff()：

ksys_mmap_pgoff() 主要完成三件事：

  1. 参数校验：检查映射长度是否合法（例如长度不能超过 TASK_SIZE、是否溢出），MAP_FIXED 时地址是否对齐等。
  2. 把 prot/flags 翻译成 vm_flags：通过 calc_vm_prot_bits() 把 PROT_READ/PROT_WRITE/PROT_EXEC 转成 VM_READ/VM_WRITE/VM_EXEC，通过 calc_vm_flag_bits() 把 MAP_SHARED/MAP_PRIVATE/MAP_ANONYMOUS/MAP_LOCKED 等转成对应的 VM_* 标志位。
  3. 取得文件对象：如果不是匿名映射，则用 fget(fd) 拿到 struct file *，随后调用 vm_mmap_pgoff()，最后 fput() 释放引用。

vm_mmap_pgoff()（mm/util.c）做的事也很简单：先对当前进程的 mm_struct 加写锁（mmap_write_lock(mm)），再调用真正的核心 do_mmap()，返回前解锁。

三、核心：do_mmap 分配虚拟地址与创建 VMA

do_mmap()（mm/mmap.c）是 mmap 实现的心脏，可以概括为「先找地址，再挂 VMA」。

1. 寻找空闲虚拟地址：get_unmapped_area

如果调用者没指定地址（addr == NULL 且未设 MAP_FIXED），内核需要为这段映射挑一块合适的区间。它会调用体系结构相关的 arch_get_unmapped_area_topdown()，从 mmap_base 开始向下搜索空闲区间——这也是 ASLR（地址空间布局随机化）的体现：mmap_base 在每次进程启动时都带有随机偏移，使得不同进程、甚至同一进程多次运行时的 mmap 地址都不同。

若指定了 MAP_FIXED，则直接使用调用者给出的地址（可能覆盖已有映射，需谨慎使用）。

2. 创建并挂接 VMA：mmap_region

找到地址后，进入 mmap_region()：

  • 调用 vm_area_alloc() 分配一个 struct vm_area_struct（VMA），并填充 vm_start、vm_end、vm_pgoff、vm_page_prot、vm_flags 等字段；
  • 如果是文件映射，执行 call_mmap()，即调用 file->f_op->mmap(file, vma)，让文件系统或驱动来「认领」这个 VMA（见第四节）；
  • 尝试与相邻的 VMA 合并（vma_merge()），合并失败则通过 vma_link() 把新 VMA 插入进程地址空间的管理结构——内核 6.1 起使用 maple tree（mm->mm_mt），更早版本使用红黑树（mm->mm_rb）加双向链表；
  • 递增 mm->map_count，并更新映射总页数 vm_total_pages。

3. vm_area_struct：一段虚拟地址的「户口本」

VMA 描述的是一段连续的虚拟地址区间及其属性，关键字段如下：

字段 含义
vm_start / vm_end 区间的起始 / 结束虚拟地址
vm_flags 访问权限与属性（VM_READ、VM_WRITE、VM_SHARED、VM_IO 等）
vm_file 关联的文件（匿名映射为 NULL）
vm_pgoff 映射在文件中的起始页偏移
vm_page_prot 页表项的保护与缓存属性（cacheable / bufferable 等）
vm_ops 指向 struct vm_operations_struct 的操作回调表
vm_private_data 驱动 / 文件系统的私有数据

关键点：到这一步为止，内核只建立了「虚拟地址 → VMA」的登记关系，页表项（PTE）还没有建立，也没有真正分配物理页。这就是所谓的按需分配（Demand Paging）/ 惰性分配——真正的物理页要等到进程第一次访问这段地址、触发缺页异常时才分配。

四、文件映射的挂接：f_op->mmap

do_mmap 里调用的 file->f_op->mmap() 决定了这段映射后续的行为。按文件类型不同，主要有两条路径：

1. 普通文件：generic_file_mmap

对 ext4 这类普通文件系统，f_op->mmap 通常指向 generic_file_mmap()（或文件系统自定义后仍落到它），它做的事非常轻量：

其中 generic_file_vm_ops 的 .fault 指向 filemap_fault()。也就是说，普通文件映射同样不在这里建立页表，而是把这个责任推迟到缺页处理阶段，由 filemap_fault() 从 page cache 里取页。

2. 设备驱动：remap_pfn_range

对字符设备等驱动，f_op->mmap 通常会在自己的 mmap 实现里直接调用 remap_pfn_range()：

它会做两件与普通文件不同的事：

  • 给 VMA 打上 VM_IO | VM_PFNMAP 标志，表示这段区域是 I/O 内存、且没有对应的 struct page（不能参与 swap，也不能被 get_user_pages() 正常对待）；
  • 立刻用给定的物理页号（pfn）和 pgprot 属性建立 PTE。驱动往往还会用 pgprot_noncached() 等把这段设备内存设为不可缓存，这正对应了之前关于 Cache 读写机制的文章里讲到的 I/O 寄存器必须 Non-cacheable 的原则。

因此，设备映射是「立即建好页表」，而普通文件 / 匿名映射是「先欠着，等缺页」。

五、缺页中断：页表与物理页的真正建立

mmap 返回用户态后，进程拿到一个虚拟地址，但此时访问它会发生什么？答案是缺页异常（Page Fault）。

完整链路

内核先通过 find_vma() 依据地址定位到对应的 VMA，再进入 handle_mm_fault()。

1. 匿名映射：do_anonymous_page

对于 MAP_ANONYMOUS 且尚未写过页的情况，内核常常映射到全局零页（zero page）；一旦要写，do_anonymous_page() 会调用伙伴系统分配一个物理页，并用 set_pte_at() 把这个页写进对应 PTE，同时建立反向映射（rmap）以便回收。

2. 文件映射：do_fault → filemap_fault

对于文件映射，do_fault() 会根据是读还是写、是否私有进一步分派到 do_read_fault()、do_shared_fault() 或 do_cow_fault()，最终都会调用 vma->vm_ops->fault()，也就是第四节挂好的 filemap_fault()：

  1. 在 mapping->i_pages（page cache 的 xarray / 基数树）里按 pgoff 查找目标页；
  2. 若命中且 PageUptodate，直接复用该页；
  3. 若未命中，则通过 mapping->a_ops->read_folio()（或预读路径）向块设备发起 I/O，把文件内容读入 page cache，并等待页变为 up-to-date；
  4. 把页填充到 vmf->page，返回给 do_fault()，后者在 finish_fault() → alloc_set_pte() 中调用 set_pte_at() 建立 PTE。

此后，用户态进程对这段地址的访问就由 MMU 通过页表直接命中物理页，不再经过系统调用——这正是 mmap 高效的原因。

3. 写时复制：do_wp_page

当 MAP_PRIVATE 的私有映射（或 fork() 出的子进程）首次对共享的只读页进行写操作时，会触发写保护缺页，进入 do_wp_page()：

  • 若该物理页的引用计数为 1，则直接改为可写，去掉写保护；
  • 否则调用 wp_page_copy() 分配一个新物理页，把原页内容复制过去，再让新页表项指向新页并置为可写。

这就是经典的 COW（Copy-On-Write）机制——MAP_SHARED 与 MAP_PRIVATE 的差异也由此产生：

MAP_SHARED MAP_PRIVATE
与文件的可见性 修改会写回文件，其他映射 / 进程可见 修改只对自己可见，不写回文件
底层机制 直接操作 page cache 中的同一物理页 首次写时触发 COW，复制出私有页
fork 后的表现 父子进程共享同一物理页 父子先共享只读页，写时各自复制

六、munmap：解映射与资源回收

munmap() 是 mmap 的逆过程，入口为 vm_munmap() → do_munmap()，核心在 unmap_region()：

  1. 遍历并清除页表：unmap_vmas() → unmap_page_range() → zap_pte_range()，对区间内每个 PTE 执行 ptep_get_and_clear()，使地址失效；
  2. 回收物理页：对每个被摘除的页执行 page_remove_rmap() 解除反向映射，并 put_page() 递减引用计数，引用计数归零时才真正归还给伙伴系统（普通文件的页通常还会留在 page cache 中供下次访问）；
  3. 释放页表与 VMA：若整级页表已空则逐级释放（free_pgtables()），并调用 remove_vma_list() 把 VMA 从 maple tree / 红黑树和链表中摘除；
  4. 刷新 TLB：最后通过 tlb_finish_mmu() 冲刷对应的 TLB 项，保证 MMU 不再缓存已失效的地址翻译。

七、总结

把整条链路串起来看：

理解这条链路后，很多看似「玄学」的现象都能得到解释：为什么 mmap 映射大文件很快（惰性 + page cache 复用）、为什么设备 mmap 需要 remap_pfn_range 并关缓存（见 Cache 属性原则）、为什么 MAP_PRIVATE 修改不影响文件（COW）。

mmap 的实现本质上是虚拟地址、VMA、页表、物理页四者之间的编排：VMA 负责「登记」一段虚拟地址的归属与属性，页表负责「翻译」，而物理页则在真正需要时才被拉进来。这套「先登记、后兑现」的惰性设计，正是 Linux 内存管理高效且优雅的核心所在。
